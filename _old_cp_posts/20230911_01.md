## Terminology
A `database system` (DBS) is a process that executes _read_ and _write_ operations
on `data item`s that are part of the DBS.

A `transaction` is a program that _submitts_ `read` and `write` operations to the `DBS`
for it to execute.

When transactions execute _concurrently_ the _interleaved execution_ of reads
and writes can produce _undersired resultes_.

_Concurrency Control_ is the activity of avoiding such undersired results.

Concurrent executions that have the same effect as serial (noninterleaved) ones
are said to be `serializable`.

The DBS can either `execute`, `delay`, or `reject` read and write operations 
submitted by transactions.

> Explain ACID

In order to adhere to the ACID principle, if an read or write operation is 
rejecrted by the DBS, then the transaction that submitted the operation is
`aborted`. If a transaction is aborted then all the transaction's reads and writes
are undone (rolledback).

The principal _reason_ for rejecting an operation is that it arrived _"too late"_.

## Multiversion
In multiversion concurrency control:
+ each __write__ to a `data_item_x` __produces__ a new copy (`version`) of x.
+ each __read__ of `data_item_x`, the DBS selects one of the existing versions of
[`data_item_x-v1`, `data_item_x-v2`, `data_item_x-v3`] to be read.

The DBS has flexibility to controlling the order of reads and write because:
+ writes do not overwrite each other
+ reads can read any version
