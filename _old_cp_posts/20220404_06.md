## Step 6: Data Persistence with PostgreSQL

> Chapter06/data_models

### Step 6.1: Install Docker Desktop Engine
For Mac we install the Docker engine
```bash
https://docs.docker.com/desktop/mac/install/
brew install --cask docker

```
> Also make sure to create an account on Docker Hub (we can think of Docker Hub as a Github for containers).

> Docker Compose relies on Docker Engine so we need to have that installed.

> Docker Desktop for Mac includes Compose along with other Docker apps, so Mac users do not need to install Compose separately.

Once docker is installed we can check if we have any __containers__ or __images__:
```bash
docker container ls -a
docker image ls
```

### Step 6.2: Configure the container with Docker-Compose

#### In: `.root/docker-compose.yml`
```yml
version: "3.7"

services:

  postgres:
    # Name of our container so that we know what it's doing when we list.
    container_name: 'to-do-postgres'
    # The container pulls the official postgres image which has everything preinstalled. 
    image: 'postgres:11.2'
    # The container will always restart if we change anything in it or if it fails.
    restart: always
    # We map incoming traffic to port 5432 and bind it to the image's port 5432.
    ports:
      - '5432:5432'
    # Generic username and passwords that should be changed for production.
    environment:
      - 'POSTGRES_USER=username'
      - 'POSTGRES_DB=to_do'
      - 'POSTGRES_PASSWORD=password'
```

### Step 6.3 Spin up the container

#### Step 6.3.1 Start the DB
Spinning up the container means that the postgres image will be pulled down
from the __Docker Hub__ website. Docker will then proceed to build the database.

```bash
docker-compose up
```

### Step 6.4: Connect DB with ORM

#### Step 6.4.1: Add __Diesel__ to __Cargo.toml__
```bash
# In Cargo.toml:
[dependencies]
diesel = {version = "1.4.4", features = ["postgres"]}
# dotenv enable us to define variables in a .env config file.
# We can use it to pass credentials to our database.
dotenv = "0.15.0"
``` 

#### Step 6.4.2: Install the __Diesel__ cli client
We want to run migrations (make changes to our database) using the terminal 
instead of the Diesel gui app, so we install the __diesel cli__.

```bash
cargo install diesel_cli --no-default-features --features postgres
``` 

#### Step 6.4.3: Define Postgres Credentials
Next we provide the credentials which will enable our __Diesel cli__ 
to connect to __Postgres__.

Credentials:
+ username : the username we use
+ password : the password we use
+ localhost : our database is running on our local machine
+ to_do : name of our database

```bash
echo DATABASE_URL=postgres://username:password@localhost/to_do > .env
``` 
This credential will be stored in the `.env` file in `.root`

Database URL's usually include the _port_ number, but we'll use the default 
(5432) which does not need to be included because it is the default port of _Postgres_.

#### Step 6.4.4: Spin up Postgres
Using _docker-compose_ we are now ready to spin up the Postgres database container.
We do that using the `docker-compose up` command. Once done, we __setup Diesel__. We'll use Diesel to _connect_ to our Postgresql database in our Docker container. 

```bash
docker-compose up
diesel setup 
``` 
This will create a __migrations__ folder in `.root`, containing an `up.sql` file (for upgrading migrations)
and a `down.sql` file (for downgrading migrations).

#### Step 6.4.5: Migration: create todo-items
We use the __diesel cli__ to generate the migrations that will create the todo-items.

#### Step 6.4.5.1: Create SQL file. In `.root/migrations/*create_to_do_items/up.sql` file:
```bash
diesel migration generate create_to_do_item
``` 

This command will add a folder to our `.root/migrations` filder.  

#### Step 6.4.5.2: Create SQL file. In `.root/migrations/*create_to_do_items/up.sql` file:

```bash
CREATE TABLE to_do (
  id SERIAL PRIMARY KEY,
  title VARCHAR NOT NULL,
  status VARCHAR NOT NULL
)
```

#### Step 6.4.5.3: Drop that DB! In `.root/migrations/*create_to_do_items/down.sql` file:
In `down.sql` we declare the db to be dropped if we are __downgrading__ the migration.

```bash
DROP TABLE to_do
```

#### Step 6.4.6: Run the migration
We are now ready to create the `to_do` table in our database.
```bash
diesel migration run
```

If we want to __reset our db__ then we can use the `redo` command.  
This will first run `down.sql', followed by running `up.sql`.

```bash
diesel migration redo
```

#### Step 6.4.7: Inspect database in Docker container
We can now inspect our database running inside our Docker container.
We will user _username_ as the username to __inspect__ that our database has
the __to_do__ table that we will connect to.

```bash

```

This will spin up a __shell interface__

## Step 6.5: Connect application to PostgreSQL
Earlier we use the _terminal_ to connect to our _db_.  
Now we want our _app_ to connect to our _db_.  

We build a funtion that will _establish a connection to our database_ in our
docker container.

#### Step 6.5.1: In `.root/src/database.rs`:
```rust
use diesel::prelude::*;
use diesel::pg::PgConnection;
use dotenv::dotenv;
use std::env;

pub fn establish_connection() -> PgConnection {
  // Ensure that the program will not throw an error if we fail to load params.
  dotenv().ok();
  // Get the database URL.
  let database_url = env::var("DATABASE_URL")
    .expect("DATABASE_URL must be set");
  // Establish a connection and return that connection.
  PgConnection::establish(&database_url)
    .unwrap_or_else(| | panic!("Error connectin to {}", database_url))
}
```

Define a __schema__ that will _map_ Rust to-do items with database data types.

#### Step 6.5.2: In `.root/src/schema.rs`:  

### Step 6.6: `Create` new Data Models and migrations
Using data models we create a 'bridge' between the containerised Postgresql database and our Rust application.

We start by creating the correct project structure by adding:  
#### Step 6.6.1 Update project structure: In `.root/src/`:
```bash
── models
│   ├── item
│   │   ├── item.rs
│   │   ├── mod.rs
│   │   └── new_item.rs
│   └── mod.rs
```
Each data model will have its own directory in _models_.
Two files, one file for a new insert, and one file for
managing the data in the db.

#### Step 6.6.2: In `.root/src/models/item/new_item_rs`:

```rust
// Import table definition.
use crate::schema::to_do;

// These are two Diesel Macros.
// The first allow the data to be insertable in our db.
#[derive(Insertable)]
#[table_name="to_do"]
pub struct NewItem {
  pub title: String,
  pub status: String,
}

impl NewItem{
  // Constructor for a new to-do item.
  pub fn new(title: String) -> NewItem {
    returrn Newitem{title, status: String::from("pending")}
  }
}
```

> The `new(title:String)` funtion could also be extended to accept a __status__ input and then build based on a match on that input, throwing an error if none of the statuses exist.

Next, we define our `item` data model, to represent (in our database) the concept
of a _to-do item_.

#### Step 6.6.3: In `.root/src/models/item/item_rs`:

```rust
// Import table definition.
use crate::schema::to_do;

// We declare with Diesel Macros that an __item__ can be queryable and identifiable. .
#[derive(Queryable, Idenfifiable)]

  pub id: i32,
  pub title: String,
  pub status: String,

```
  
Finally, we update the following files for our changes to have an effect:
