# Orientation
MLIR is a ... of LLVM.
LLVM is a ....
MLIR, or Multi-Level Intermediate Representation, is part of the LLVM project. MLIR was desiged to be even more flexible than LLVM.
`Operations` are the core unit of _abstraction_ and _computation_.
Operations are modelled using a small set of conceptes:
+ Name of the operation 
+ List of Single Set Abstraction operand values
+ List of `Attributes`
+ List of `Types`
+ Source location : every operation has a mandatory source location.
+ Blocks
+ Regions 

```js
%t_tensor = "toy.transpose"(%tensor) {inplace = true} : (tensor<2x3xf64>) -> tensor<3x2xf64> loc("example/file/path":12:1)
```

# Opaque API
MLIR can be used to customize all IR elements (attributes, operations, and types).

```scala

      return %t_tensor : tensor<3X2Xf64>
      loc 
}
```

+ (%tensor) : a list of zero of more input operatnds/arguments
+ { inplace = true }

# MLIR Dialect
A `dialect` provide a groupig mechanism for abstraction under a unique namespace.

## MLIR C API
Writing actual MLIR source is pretty verbose and cumbersome.
Fortunately there's an extensive C API that can be used to bind other langauges with.

More or less every `type` exposed by MLIR is _an opaque pointer_ to a `concrete C++ type`.

```cpp
// mlir/include/mlir-c/IR.h
#define DEFINE_C_API_STRUCT(name, storage) 
struct name {                                                      
storage *ptr;
};                                              
typedef struct name name
```

## Owned versus Referenced Values
We need to know if a type is owned or a refernce.
We can discern this by looking at the functions the different types in MLIR have.

If the type has the functions `mlirXCreate()` and `mlireXDestroy()` then the object is an `owned` value.

If the type has the function `mlirGet()` then it is a unique and referenced value.
This mechanism is called __[interning](https://en.wikipedia.org/wiki/String_interning)__.

> The MLIR C API does __not__ differentiate between "owned value that we can own" and "owned value that we can borrow". This means that we can __destroy__ values that we __do not own__ (using `mlirXDestroy()`) and also that we might create _dangling pointers_ if we destroy a value that we own and that others depend on.

# Rust Bindings to MLIR
We want to generate Rust bindings to the MLIR C API. How?
Fortunately, we can use __`bindgen`__.
Let's do that.

Using [rust-bindgen](https://rust-lang.github.io/rust-bindgen/), a C header like:

```c
typedef struct CoolStruct {
    int x;
    int y;
} CoolStruct;

void cool_function(int i, char c, CoolStruct* cs);
```

will generate Rust FFI code that we can use to call it, looking like:

```scala
/* automatically generated by rust-bindgen 0.99.9 */

#[repr(C)]
pub struct CoolStruct {
    pub x: ::std::os::raw::c_int,
    pub y: ::std::os::raw::c_int,
}

extern "C" {
    pub fn cool_function(i: ::std::os::raw::c_int,
                         c: ::std::os::raw::c_char,
                         cs: *mut CoolStruct);
}
```

# Working with MLIR using Rust
Now that we have our Rust bindings to the MLIR C API, let's put it to use. First we need to _initialize the runtime_.
We do that by creating an `mlirContext` object.

```scala
mod ffi; // import the generated mlir bindings.

let ctx = unsafe { ffi::mlirContextCreate()};
unsafe {ffi::mlirContextDestroy(ctx)};


struct Context {
  inner: ffi::MlirContext,
}

impl Context {
  pub fn create() -> Option<Context> {
    let inner = unsafe { ffi::mlirContextCreate()};

  // The API call might return a NULL value so we need to protect against that.
    if inner.ptr.is_null() {
      return None;
    }

    Some(Context { inner })
  }
}

impl Drop for Contect {
  fn drop(&mut self) {
    unsafe { ffi::mlirContextDestroy(self.inner)}
  }
}
```

# Lifetime of an MLIR Context
If we have the power to create MLIR context objects then we have to make sure that we also handle its lifetime.
We can do so by either using _lifetimes_, _put the context in an Arc_, or choose _not_ to expose the context to the API consumer so that there is no risk of any dangling pointers.

```scala
impl SpringAttr {
  pub fn get(s: &str) -> StringAttr;
{}}
```

So we get

```scala
use std::sync::Mutex;
use once_cell::OnceCell;

static CONTEXT: OnceCell<SyncContext> = OnceCell::new();
pub(crate) fn context() -> &'static SyncContext {
  CONTEXT.get_or_init(
    || SyncContext {
      context: Context::create().unwrap(),
      mutex: Mutex::new(()),
    }
  )
}
```

# Accessing Unique Types
MLIR synchronizes the access to _unique types_ based on context. Somethings called __[operation passes](https://mlir.llvm.org/docs/PassManagement/#operation-pass)__ explain how this works. Basically, all _passes_ in MLIR:

1. Must not modify the state of another operation that is not nested within the current operation being operated on.  
  Why? Because other threads might be operating on these operations simultaneously.
2. Must not inspect thet state of sibling operations.  
  Why? Because other threads might be modifying these operations in parallel.

We handle this by having a `SyncContext` object.

```scala
struct SyncContext {
  context: mlir::Context,
  mutex: Mutex<()>,
}

impl SyncContext {
  fn without_mutex<F, T>(&self, f:F) -> T
  where
    F: FnOnce(ffi::MlirContext) -> T,
    {
      f(self.context.inner)
    }
  
  fn with_mutex<F, T>(&self, f:F) -> T
  where
    F: FnOnce(ffi::MlirContext) -> T,
    {
      let guard = self.mutex.lock():unwrap();
      f(self.context.inner)
    }
}
```

# Example: Grassmann Algebra
Let's explore how to use MLIR with Rust bindings generated for the MLIR C API.
We will create a Domain-Specific Language (DSL) for the key operations in Grassmann Algebra.

These are the steps we will follow:
1. Define the DSL
2. Create the MLIR Dialect
3. Write the code in Rust
4. Lower
5. Optimize
6. Lower the MLIR code to LLVM IR
7. Compile the LLVM IR to machine code
8. Execute the generated machine code

## Step 1/8: Define the DSL
We start by defining the syntax of our DSL `Grassmann`:
+ `grassmann_add(A,B)` : Add matrices A and B
+ `grassmann_sub(A,B)` : Subract matrix B from A
+ `grassmann_mul(A,B)` : Multiply matrices A and B

## Step 2/8: Create the MLIR Dialect
To interface with MLIR we define a dialect.
The dialect will model the structure of our language.
We use Rust to define the dialect, but we could also have used C++ or the 
declarative specification tool: tablegen.


```cpp
/// This is the definition of the Grassmann dialect.
/// The dialect will inherit from mlir::Dialect. We use it to register custom
/// attributes, operations, and types.
class ToyDialect : public mlir::Dialect {
  public:
    explicit ToyDialect(mlir::MLIRContext *ctx);

    /// We provide a utility accessor to the dialect namespace.
    static llvm::StringRef getDialectNamespace() { return "toy"; }

    /// An initializer called from the constructor of ToyDialect that is used to
    /// register attributes, operations, types and more within the Toy dialect.
    void initialize();
};
```

> Once the dialect has been defined, it can be loaded into an MLIRContext:

```shell
context.loadDialect<ToyDialect>();
```

> By default, an `MLIRContext` will only load the __Builtin Dialect__ (which provides a few core IR components). Other dialects, like our Toy dialect, must be explicitly loaded.
