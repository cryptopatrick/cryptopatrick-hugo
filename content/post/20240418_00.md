# Why SQLx
SQLx enable us to check for query consistency at compile time.
It's also runtime-agnostic so we  can use it with sqlite, mysql, postgres, etc.


# Get Started

```shell
# We add sqlx *dependency* to our Rust project.
cargo add sqlx
# We install the *binary* cli which makes using sqlx easier
cargo install sqlx-cli 
```

# Database Migrations
Instead of manually creating database tables, we can programmatically create SQL schems which does the same.
We store the code for doing so in `.sql` files. This is called _migrations_.

```sql
# stored in ../schema.sql
CREATE TABLE IF NOT EXISTS person (
  id SERIAL PRIMARY KEY,
  name TEXT
);
```

We can execute the migration like so...
```shell
# Using the sqlx-cli, with -r flag making the migration reversible
sqlx migrate -r add schema.sql
```

# Queries
Running a sql query

```scala
// 
let query = sqlx::query("SELECT * FROM TABLE")
  .execute(&pool).await.unwrap();

// Insert data into database
sqlx::query("INSERT INTO TABLEW (person) VALUES ($1)")
  .bind("Deckard".to_string())
  .execute(&pool).await.unwrap();
```

If we fetch data from the db it can be handy to iterate over all 
the returned results, of which there might be many.

```scala
#[derive(sqlx::FromRow)]
struct Person {
  id: i32,
  name: String,
}

asunc fn person(pool: PgPool) -> Vec<Person> {
  let res = sqlx::query_as::<_,Person>("Select * FROM PERSON")
    // Get all the results.
    .fetch_all(&pool).await.unwrap();

  Ok(res)
}

// Query returning the result as a tuple, which might be handy
// if we don't know the number of fields (Name, Age, Address).
let query = sqlx::query_scalar("SELECT * FROM PERSON LIMIT 1")
  .fetch_one(&pool).await.unwrap();

println!("{:?}", query.0);
```


# Compile Time Query Check
Enable us to guarantee that our SQL queries are correct.
`query!` and `query_as!` are two macros which help with this.
Using `cargo sqlx prepare` will generate JSON files for our queries. These are then used for compile time query checking.

```scala
// note that bound parameters are added to the query macro
let query = query!("SELECT * FROM FOO WHERE ID = $1", 1)
  .fetch_one(&pool).await.unwrap();
```

> There's a [gotcha](https://docs.rs/sqlx/latest/sqlx/macro.query.html#type-overrides-output-columns) when using Postgres and compile time checking.


## Handy Feature 1
We can store queries in a file and then run that using a macro.

```shell
# In query.sql
SELECT * FROM PERSON WHERE id = $1;

# In main.rs
let query = query_file!("query.sql", 1i32).fetch_one(&pool)
  .await.unwrap();

# Also checkout: query_file_as! and query_file_scalar!.
```

> Adding `unchecked` to a query (query! becomes query_unchecked!) will only check syntax and not if the database inputs and outputs are correct for that query macro.

# Postgres Powers
We can use `pg_notify` as an event listener, to let Postgres inform us when records are upated.

```scala
let mut listener = PgListener::connect_with(&pool).await.unwrap();
listener.listen("testNotify").await.unwrap();
// set up a loop to listen for notifications.
tokio::spawn(async move || {
  while let Some(notification) = listener
    .try_recv().await.unwrap();
  println!("{notificaiton:?}");
});

loop {
  sqlx::query("SELECT pg_notify('testNotify', 'Hello world')")
    .execute(&pool).await;
}

// Also explore more advanced features: .into_stream().
```

## Handy Feature 2
We can move the notification feature into SQL (intead of Tokio).
Add the following to our sql migraion file `schema.sql` .

```sql
CREATE TABLE IF NOT EXISTS test_table (
  id SERIAL PRIMARY KEY,
  message TEXT NOT NULL
);

CREATE TRIGGER "testNotify"
AFTER INSERT ON test_table
FOR EACH ROW EXECUTE PROCEDURE testNotify();

CREATE OR REPLACE FUNCTION testNotify()
  RETURNS TRIGGER AS $$
DECLARE
BEGIN
  PERFORM pg_notify('testNotify', ROW_TO_JSON(NEW)::text);
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```
