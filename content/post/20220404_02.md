### Step 2.2: Create structs to model the domain
We model the domain of our application by expressing _things (a todo-list item)_ as structs and _processes (deleting a todo-list item)_ as traits.

We start by creating a _base_ todo-item struct from which other todo-item types (pending, done, etc) will inherit attributes:

#### In: `.root/src/to_do/structs/base.rs`  

```scala
// A base struct to represent a todo-item.
pub struct Base {
  pub title: String, // name of todo-item
  pub status: String // pending or done?
}

// Constructor for Base struct.
// Please note _pub_ keyword before the fn, which we
// need since we want to make the constructor available
// outside of the file, inside the module (not outside)
impl Base {
    pub fn new(input_title: String, input_status:String) -> Self {
        return Base{
            title: input_title, 
            status: input_status
        }
    }
}
```


### Step 2.3: Extend `base` class to `pending` and `done`
We extend the base struct by coding two more structs to handle todo-items that are either __done__ or __pending__:

> In the next section, the code for __done.rs__ and __pending.rs__ are the same except for the names Pending and Done.

#### In: `.root/src/to_do/structs/done.rs` and `.root/src/to_do/structs/pending.rs`

```scala
// To reach the base.rs file we need to 
// reach up to the mod.rs file in to_do using the super keyword.
use super::base::Base;

// In contrast to Base, we want Done to be
// available outside the structs module.
 pub struct Done{
    pub base: Base
}

impl Done{
    pub fn new(input_title: &str) -> Self {
        Done{
            base: Base::new(input_title, "done")
        }
    }
}
```

### Step 2.4: Make structs reachable from main
In order to make the base::new() constructor available to the rest of the module we need to add `mod base` to our `.root/src/to_do/structs/mod.rs` file, in the directory in which the files resides. We don't want to export `mod base` so we don't make it `pub`.

Since __done.rs__ and __pending.rs__ are coded, we can also add them to `.root/src/to_do/structs/mod.rs` file, so that they are accessible from our __main.rs__ file:

#### In: `.root/src/to_do/structs/mod.rs` 

```scala
// We only want our base structs to be used within the same module (and not outside of it), so we keep it private by not adding the pub keyworkd infront of _mod base_
mod base;
// Made public to be reachable from main.rs
pub mod done; 
pub mod pending;
// We import the traits module since we know we'll be using that as well
pub mod traits;
```

### Step 2.5: Make the structs publicly available
We can now make the structs avaiblable to `.root/src/main.rs` by publicly defining the `to_do/structs` module in `.root/src/to_do/mod.rs`

#### In: `.root/src/to_do/mod.rs`
```scala
pub mod structs;
```

### Step 2.6: Scalability with the Factory Design Pattern

> Our factory becomes the interface with which we interact with the struct building module.

To keep things scalable we use the Factory pattern here. This means that we check the input type to the
function and build the struct depending on that type.
If the type is not accepted we return an error.

#### In: `.root/src/to_do/mod.rs`

```scala
// Import the structs module
pub mod structs;

use structs::done::Done;
use structs::pending::Pending;

// Used by the factory pattern.
pub enum ItemTypes {
    Pending (Pending),
    Done (Done)
}

// Using the Factory Pattern
// This function builds and returns a to_do struct.
pub fn to_do_factory(item_type: &str, item_title:&str) 
    -> Result<ItemTypes, &'static str> {
        match item_type {
            "pending" => Ok(ItemTypes::Pending(Pending::new(item_title))),
            "done" => Ok(ItemTypes::Done(Done::new(item_title))),
            _ => Err("to_do_factory rejected the input.")
        }
}
```

Finally we add the whole __to_do__ module to our `.root/src/main.rs` file.  

#### In: `.root/src/main.rs`
```scala
mod to_do;
// p.45
// use to_do::structs::done::Done;
// use to_do::structs::pending::Pending;
use to_do::to_do_factory;

fn main() {
  // Create a todo struct depending on the input.
  // let item = to_do_factory("some input");
  todo!()
}
```

### Step 2.7: Interacting with the outside
We want to be able to __load, edit, save__ the state
of todo-items. we also want to accept user input/commands to edit and display data.

1.  Collect args from user
2.  Interpret a command from user provided args
3.  Fire a function based on interpreted command
4.  Load/edit/save a JSON with the state of todo-items

#### Step 2.7.0 In: `.root/`
We will store todo data using a __json__ file. In __.root__ create a new json file.  
```bash
touch state.json
# Make file proper json
echo {} >> state.json
```

#### Step 2.7.1 In: `.root/Cargo.toml`
Next, to allow us to serialize data into json format we add the following dependency:

```bash
[dependencies]
serde_json = { version = "1.0", default-features = false, features = ["alloc"] }
```

#### Step 2.7.2 In: `.root/src/state.rs`
We create a file that will contain the functions necessary to __read__ and __write__ to our __state.json__ file.

```scala
use std::fs::File;
use std::fs;
use std::io::Read;

use serde_json::Map;
use serde_json::value::Value;
use serde_json::json;

// Read a json file from disk.
pub fn read_file(file_name: String) -> Map<String, Value> {
    let mut file = File::open(file_name).unwrap();
    let mut data = String::new();

    file.read_to_string(&mut data).unwrap();
    dbg!(file);
    let json:Value = serde_json::from_str(&data).expect("Failed to read file");
    let state:Map<String, Value> = json.as_object().unwrap().clone();

    state
}

// Write to a json file on disk.
pub fn write_to_file(file_name: String, state:&mut Map<String, Value>){
    let new_data = json!(state);
    fs::write(file_name, new_data.to_string()).expect("Failed to write to file.");
}
```




### Step 2.8: Adding functionality with traits
Inside `.root/src/to_do/structs/traits` we start adding traits for each process we want to model. We create
one file for each process(trait) that we want to add:

+ __get__ : print details about a to-do item
+ __edit__ : set an item to _pending_ or _done_.
+ __create__ :
+ __delete__ :

#### Step 2.8.1 In: `.root/src/to_do/structs/traits/get.rs`

```scala
use std::option::Option;
use serde_json::Map;
use serde_json::value::Value;

// Trait for getting to_do items.
pub trait Get {
    // We take the _state_, call the _get_ function fo the _map_
    // manage it with match and print the todo-items to console.
    fn get(&self, title: &String, state: &Map<String, Value>) {
        let item: Option<&Value> = state.get(title);
        match item {
            Some(result) => {
                println!("Item:{}", title);
                println!("Result:{}", result);
            },
            None => println!("Item: {} was not found.", title)
        }
    }   
}
```

#### Step 2.8.2 In: `.root/src/to_do/structs/traits/edit.rs`

```scala
use serde_json::Map;
use serde_json::value::Value;
use serde_json::json;

// We insert the state and import our
// write_to_file function.
use crate::state::write_to_file;

pub trait Edit{
    fn set_do_done(&self, title: &String, state: &mut Map<String, Value>) {
        state.insert(title.to_string(), json!(String::from("done")));
        write_to_file(String::from("./state.json"), state);
        println!("\n\n{} is being set to done\n\n", title);
    }
    
    fn set_to_pending(&self, title:&String, state: &mut Map<String, Value>) {
        state.insert(title.to_string(), json!(String::from("pending")));
        write_to_file(String::from("./state.json"), state);
        println!("\n\n{} is being set to pending\n\n", title);
    }
}

```

#### Step 2.8.3 In: `.root/src/to_do/structs/traits/create.rs`

```scala
use serde_json::Map;
use serde_json::value::Value;
use serde_json::json;

// We insert the state and import our
// write_to_file function.
use crate::state::write_to_file;

// Trait for creating to_do items.
pub trait Create{
    fn create(&self, title: &String, status: &String, state: &mut Map<String, Value>){
        state.insert(title.to_string(), json!(status));
        write_to_file(String::from("./state.json"), state);
        println!("\n\n{} is being created\n\n", title);
    }
}

```

#### Step 2.8.4 In: `.root/src/to_do/structs/traits/delete.rs`
```scala
use serde_json::Map;
use serde_json::value::Value;

use crate::state::write_to_file;

// Trait for deleting a to_do item.
pub trait Delete{
    fn delete(&self, title:&String, state: &mut Map<String, Value>) {
        state.remove(title);
        write_to_file(String::from("./state.json"), state);
        println!("\n\n{} is being deleted\n\n", title);
    }
}
```

> Our traits can now interact with the `state.json` file.

### Step 2.9: export traits and connect traits to structs
We need to make our traits available to the outside.
We do so by adding them to `.roots/src/to_do/structs/traits/mod.rs`.

#### In: `.root/src/to_do/structs/traits/mod.rs` add:

```scala
pub mod create;
pub mod edit;
pub mod get;
pub mod delete;
```

We also have to make the traits available to the structs.
We do so by defining them in `.root/src/to_do/structs/mod.rs`:


```scala
pub mod traits;
pub mod done;
pub mod pending
mod base;
```


Our __structs__ can now use the keyword __super__ to access these __traits__.
Let's empower our structs with these traits.

> We initially worked on done.rs and pending.rs in step 2.3.

#### In: `.root/src/to_do/structs/done.rs` add:
```scala
// To reach the base.rs file we need to
// reach up to the mod.rs file in to_do
// using the super keyword.
use super::base::Base;
use super::traits::get::Get;
use super::traits::delete::Delete;
use super::traits::edit::Edit;

impl Get for Done{}
impl Delete for Done{}
impl Edit for Done{}


// In contrast to Base, we want Done to be
// available outside the structs module so we make it pub
pub struct Done {
    pub super_struct: Base
}

impl Done {
    pub fn new(input_title: String) -> Self{
        let input_status: String = String::from("done");
        let base: Base = Base::new(input_title, input_status);
        
        Done{super_struct:base}
    }
}
```

### Step 2.10 Direct flow of commands
To keep things scalable, we create an interface `src/processes.rs` that we'll use to direc the flow of comands. It will only hold a few functions and therefore, just as `state.rs`, will be located in `.root/src`, instead of in its own _module_.

#### In: `.root/src/processes.rs`
```scala
/// Purpose of this module is to direct the flow of commands.

use serde_json::Map;
use serde_json::value::Value;

use super::to_do::ItemTypes;
use super::to_do::structs::done::Done;
use super::to_do::structs::pending::Pending;
use super::to_do::structs::traits::get::Get;
use super::to_do::structs::traits::create::Create;
use super::to_do::structs::traits::delete::Delete;
use super::to_do::structs::traits::edit::Edit;

// Process command on a pending to_do
fn process_pending(item: Pending, command: String, state: &Map<String, Value>){
    let mut state = state.clone();
    match command.as_str(){
        "get" => item.get(&item.base.title, &state),
        "create" => item.create(&item.base.title, &item.base.status, &mut state),
        "delete" => item.delete(&item.base.title, &mut state),
        "edit" => item.set_do_pending(&item.base.title, &mut state),
        _ => println!("command: {} not supported.", command)
    }
}

// Process command on a done to-do
fn process_done(item:Done, command: String, state: &Map<String, Value>){
    let mut state = state.clone();
    match command.as_str() {
        "get" => item.get(&item.base.title, &state),
        "delete" => item.delete(&item.base.title, &mut state),
        "edit" => item.set_to_done(&item.base.title, &mut state),
        _ => println!("command: {} not supported", command)
    }
}

// Entro point for pending and done processing, so that's why it's public.
pub fn process_input(item: ItemTypes, command: String, state: &Map<String,Value> ) {
    match item {
        ItemTypes::Pending(item) => process_pending(item, command, state),
        ItemTypes::Done(item) => process_done(item, command, state),
    }
}
```

### Step 2.11 update `main.rs`

#### In: `.root/main.rs`
Finally, we can update our `main.rs` file to reflect the changes we've made:

```scala
mod state;
mod to_do;
mod processes;

use std::env; // To handle args passed by the user.
use state::read_file; // To load the state of the to_do-list.
use serde_json::value::Value;
use serde_json::Map; // To store the state.
use to_do::to_do_factory; //  Used to create to-do's.
use processes::process_input; // Provides functionality for processing commands.

fn main() {             
    // Collect args from the user.
    let args: Vec<String> = env::args().collect();
    // Save passed parameters.
    let command: &String = &args[1];
    let title: &String = &args[2];         
    // Read json file to get the state of the todo list.
    let state: Map<String, Value> = read_file(String::from("./state.json"));
    // define outside of match scope
    let status: String;
    
    match &state.get(*&title){
        Some(result) => {
            status = result.to_string().replace('\"', "");
        }
        None => {
            status = String::from("pending");
        }
    }
    // Create a to_do struct depending on the input.
    let item = to_do_factory(&status, title.to_string()).expect(&status);
    // Affect the state based on the struc tand command passed into the program
    process_input(item, command.to_string(), &state);
}
```
